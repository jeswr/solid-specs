This specification defines y-protocol-v1, the profile of the Solid Storage Service Description's CRDT sync service for documents edited with Yjs. A Yjs document lives in a container of a Solid or Linked Web Storage storage as a log of update resources. Clients without a relay collaborate by writing and reading those resources. A relay adds real-time exchange and presence over WebSocket: clients obtain a short-lived ticket, the relay authorizes every message it delivers or accepts against the storage's access control at that moment, persists what it accepts into the same container, and passes on what other clients write there. The specification fixes the byte layout of the stored resources, the rules for loading and compacting the log without losing updates, and the ticket exchange.

This is an unofficial personal draft. It is not a work item of the W3C Solid Community Group or of any W3C Working Group, and its identifier is minted under a personal namespace until a venue adopts it. It completes the ssd:CrdtSyncService entry of [[SOLID-SD]], which names this profile and leaves its protocol to this document.

This draft was prepared with the assistance of AI systems operated on behalf of the editor (drafting: Claude Opus 5.5). The editor is responsible for all content. Issues are welcome on the GitHub repository.

Introduction

Motivation

Collaborative editors such as the suite's Docs, Sheets and Notes keep their documents as Yjs documents. A Yjs document is a set of updates: applying the same updates in any order, any number of times, gives the same document. That property lets a document live in a storage as a container of small, write-once resources, one per update, which any client with access can append to without a read-modify-write race.

A log of resources gives eventual consistency with latency of seconds and no presence. A relay gives both, but a relay that only checks access when a connection opens keeps sending a document to someone whose access was revoked, and a relay that keeps its own copy of the document splits it from the log. This profile ties the two together: one storage encoding, one loading rule, one compaction rule, and a relay that is a reader and writer of the same log, bound to the storage's access control for every message.

Overview

A storage that offers a relay lists a ssd:CrdtSyncService whose dcterms:conformsTo names this profile, with the ticket endpoint as its service endpoint [[SOLID-SD]]. 

<https://pod.example/> did:service
    [ a ssd:CrdtSyncService ;
      did:serviceEndpoint <https://pod.example/.sync/tickets> ;
      dct:conformsTo ssd:y-protocol-v1 ] .

A client that edits the document in the container https://pod.example/docs/plan/:

  1. loads the document by reading every update and snapshot resource in the container ();
  2. requests a ticket by sending {"room": "https://pod.example/docs/plan/"} to the ticket endpoint with its storage credentials, and receives a WebSocket URL and an expiry ();
  3. opens the WebSocket and exchanges Yjs sync and awareness messages with the relay ();
  4. without a relay, or while disconnected from it, writes each change as a new update resource in the container ().

This specification defines four conformance classes. A storage server is a storage server as [[SOLID-SD]] defines it that offers a relay for its storages. A relay is the server component behind a ssd:CrdtSyncService that conforms to this profile. A client is software that reads or edits a room, with or without a relay. A compactor is a client or relay that compacts a room; it meets the requirements on its own class and those of .

The machine-readable list of this specification's normative statements is the companion document spec.statements.ttl. The test vectors in vectors/ are normative for the byte layout and the loading rule: where the prose and a vector disagree, report it as an issue. Examples are informative.

Terminology

This specification uses the terms storage, storage server, service, service endpoint and service URL as [[SOLID-SD]] defines them, and the terms update, state vector and client ID as [[YJS]] defines them.

room
A container in a storage that holds one Yjs document as a log of update and snapshot resources. The container's IRI identifies the room and the document.
update resource
A non-container resource in a room whose body is a JYU1 record ().
snapshot resource
A non-container resource in a room whose body is a JYS1 record: an update that holds the content of other update and snapshot resources it replaced.
log resource
An update resource, a snapshot resource or a legacy update resource ().
room state
The Yjs document a client or relay holds for a room.
connection
A WebSocket connection between a client and a relay, opened with a ticket, bound to one room and one agent.
may read the room
An agent may read the room when the storage's access control lets it read the room container and every log resource in it.
may write the room
An agent may write the room when it may read the room and the storage's access control lets it create log resources in the room container with the requests this specification describes (in Web Access Control [[WAC]], the access modes the storage requires for those requests, such as acl:Append on the container and, for a PUT, acl:Write on the new resource as its inherited access control gives it).
authorization context
Everything besides the agent that the storage's access control takes into account for a request: in Web Access Control the request's Origin, in Solid-OIDC the client identifier, and any grant the request presents. "May read" and "may write" are always decided for an agent in an authorization context.
confirmed
The creation of a resource is confirmed when the storage answered the request that created it with 201 Created or another 2xx status other than 202 Accepted, or when the creator has since read the resource and found the body it wrote. A 202 Accepted answer alone confirms nothing [[RFC9110]].
valid payload
A byte string that the Yjs v1 update decoder [[YJS]] decodes with no bytes left over, and that applies without error to a new, empty Yjs document.

The profile IRI is https://jeswr.org/ns/solid-sd#y-protocol-v1, written ssd:y-protocol-v1.

Storage encoding

A log resource body is a 16-byte header followed by a Yjs update. The header lets a reader tell an update from a snapshot and order resources without relying on their names, which a Linked Web Storage server chooses.

BytesFieldContent
0–3magic4A 59 55 31 (ASCII JYU1) for an update, 4A 59 53 31 (ASCII JYS1) for a snapshot
4–11timeunsigned 64-bit big-endian integer: milliseconds since 1970-01-01T00:00:00Z when the writer created the record
12–15nonce4 bytes chosen at random by the writer
16–endpayloada Yjs update in the v1 update encoding [[YJS]]

A client or relay that writes a log resource MUST write a body laid out as in the table above, with a valid payload.

The time field MUST NOT exceed 253 − 1.

A writer MUST draw the nonce from a cryptographically secure random source.

A reader MUST treat a body as a valid log record only when it is at least 16 bytes long, begins with one of the two magic values, has a time field no greater than 253 − 1, and has a valid payload.

The ordering key of a log resource is the triple (time, nonce read as an unsigned 32-bit big-endian integer, resource IRI compared by code point). Yjs gives the same document in any order of application; the key only makes loading deterministic.

A writer MUST create log resources with the media type application/octet-stream.

A reader MUST decide whether a resource is an update resource or a snapshot resource from its body, not from its media type or its name.

No client or relay may change the body of a log resource after it is created: a writer MUST NOT send a PUT or PATCH request to an existing log resource.

Legacy update resources

Version 0.1 of @jeswr/y-solid writes each update with no header, as a resource named with a 15-digit zero-padded millisecond time, a hyphen and a UUID, for example 001761480000000-0f8e2c6a-3b1d-4f5e-9a7c-2d4b6e8f0a1c. Rooms it wrote can be read under this profile.

A legacy update resource is a non-container resource in a room whose body does not begin with either magic value, whose last path segment matches ^[0-9]{15}-[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$, and whose whole body is a valid payload. Its ordering key is (the 15-digit time, 0, resource IRI).

A reader SHOULD apply legacy update resources as it applies update resources.

A writer MUST NOT create a legacy update resource.

A Yjs v1 update whose first four bytes equal a magic value would have to hold structures for 74 clients, the first with 89 structures and client ID 85 (JYU1) or 83 (JYS1); Yjs draws client IDs at random from 232 values, so a legacy update is not mistaken for a headed one in practice.

The update log

Writing updates

A client that writes a change to a room without a relay MUST create a new update resource in the room container whose payload holds the change, using a request that cannot replace an existing resource: POST to the container, or, on a Solid storage only, PUT with If-None-Match: *.

A writer that suggests a name for a log resource MUST include at least 32 random bits in it.

Names such as 01761480000000-k3v9q2xa.yupdate and snapshot-01761480000000-p8m2w7cd.ysnap (13-digit time, eight base32 characters) are a convenient choice. Unique names make it unlikely that a deleted record's IRI is reused; conditional deletion with a strong entity tag () makes sure that a reused IRI is never deleted by mistake.

A client or relay MUST NOT create a container inside a room.

Loading a room

A client or relay loads a room by listing the room container, reading each log resource it lists and applying the payloads to its room state. Compactors replace resources while others load (), so a reader keeps listing until a listing shows nothing new.

A complete listing is a listing of the room container's members that reflects one state of the container: a single unpaginated response, or every page of a paginated listing where the membership tag of the room container was the same before the first page was requested and after the last page was received. The membership tag is the strong entity tag of the room container itself, returned by a HEAD request on the container IRI, not the entity tag of a page. Because the storage never gives a container the same membership tag for two different moments separated by a membership change, equal tags before and after mean no member was added or removed in between.

A reader MUST NOT use a listing that is not a complete listing to decide that a room is loaded; when the membership tag changed during a paginated listing, or the storage gave none, it MUST list again.

A reader MUST send every request for a listing page, a membership tag or a log resource, and every request that confirms an entity tag, with Cache-Control: no-cache [[RFC9111]], so that no cache answers it without the storage validating the answer.

A reader MUST apply every valid update resource, every valid snapshot resource and, when it supports them, every legacy update resource that it reads in the room, and MUST NOT leave one out because of its time, its name, or the presence of a snapshot resource with a later time.

A reader MUST NOT treat the room as loaded until it holds a complete listing every log resource of which it has read and applied, or found invalid.

For a resource that it read before that complete listing began, a reader MUST confirm that the resource still has the strong entity tag it read, for example with a conditional request, and MUST read it again when it does not.

When a resource that a listing named is gone when read (404 Not Found or 410 Gone), a reader MUST list the room container again and read every log resource in the new listing that it has not yet read.

A reader MAY stop after a number of listings of its choosing, but MUST then report that the load did not complete and MUST NOT report the room as loaded.

A reader MUST NOT apply any part of a resource in a room that is not a valid log record or a legacy update resource it supports, and SHOULD report it.

A reader MUST apply each payload so that its room state is unchanged when the payload cannot be applied without error, for example by applying it to a copy of the room state first.

A reader SHOULD apply log resources in ascending order of their ordering keys.

A reader MUST ignore containers inside a room.

Compaction keeps every update in some log resource at every moment, so the resources named in a complete listing hold every update that existed when the container was in that state. A resource gone between listing and reading was replaced by a snapshot resource that the next listing names. Reading a record twice is harmless, because applying an update twice changes nothing.

Watching a room without a relay

A client may subscribe to notifications on the room container [[SOLID-NOTIFICATIONS]] and read each log resource reported as created. This gives eventual consistency within seconds, with no presence.

A client that relies on notifications to learn of new log resources MUST load the room again whenever it cannot tell whether it missed a notification, such as after its subscription lapsed or its channel reconnected.

Compaction

A room grows by one resource per write. A compactor replaces a set of log resources with one snapshot resource that holds their content, then deletes them. Several compactors may work on a room at once, offline or online; the rules below keep every update in some resource at every moment, whatever their interleaving.

A compactor that compacts a set R of log resources MUST first create a snapshot resource whose payload is a Yjs update containing the content of every resource in R, using a request that cannot replace an existing resource.

A compactor MUST build the snapshot payload only from log resources of the room that meet , for example by applying them to a new, empty Yjs document, and MUST NOT include content that it holds from any other source.

A compactor MUST NOT delete a resource in R until the creation of that snapshot resource is confirmed.

A compactor MUST NOT delete a resource unless it read the whole body of that resource, found it to be a valid log record or a legacy update resource, and applied it to the room state from which it built the snapshot.

When the compactor's room state holds content that Yjs has not yet integrated because it depends on updates the compactor has not seen, the snapshot payload MUST include that content, or the compactor MUST NOT delete the resources that carried it.

A compactor MUST send each deletion with an If-Match header carrying the strong entity tag it received when it read that resource, and MUST NOT delete a resource for which it received no strong entity tag.

A storage server MUST send a strong entity tag with every successful read of a log resource, and MUST give a resource that moves to another container a strong entity tag it has not had before, so that a conditional request prepared in one room never matches it in another.

A storage server that paginates the listing of a container MUST give the container a membership tag that, after any member is added to or removed from it, differs from every membership tag the container had before, even when the set of members returns to an earlier state.

A compactor MUST NOT compact a resource unless it has confirmed, after reading the resource, that the resource has no access control of its own and inherits the room container's.

A compactor MUST treat a 404 Not Found or 410 Gone answer to a deletion as success, and a 412 Precondition Failed answer as a resource it must leave in place.

A client MUST NOT compact a room that it may not write.

A client MUST NOT give a log resource access control of its own.

Every deleted resource's content is in a snapshot resource that existed before the deletion. A later compactor that deletes that snapshot has, by the same rules, first written a newer snapshot holding it. Two compactors that read overlapping sets each write a snapshot holding everything they read, so a resource deleted by one is still held by the other's snapshot or by the first one's. A loader that reads every log resource therefore always sees every update. Compaction removes history: a storage that offers a versioning service keeps earlier versions as [[SOLID-SD]] describes.

This profile protects a room as a whole. Compaction moves content between resources, and the relay merges the whole log into one state, so an agent who may read the room may in time read every update ever written to it. Content meant for fewer readers belongs in another room. In Web Access Control a compactor confirms inheritance by finding that the resource's ACL resource does not exist, which needs acl:Control on the room in general; a compactor that cannot confirm it does not compact, and leaves compaction to the relay or to an agent who can. Access control that someone sets on a record after it was readable to the whole room does not withdraw what readers already saw.

Tickets

The relay speaks WebSocket, and browsers cannot attach the storage's credentials to a WebSocket handshake. A client therefore exchanges its credentials for a ticket over HTTP first. The ticket endpoint is the service endpoint of the ssd:CrdtSyncService.

Requesting a ticket

A client requests a ticket by sending a POST request to the ticket endpoint with an application/json body: a JSON object whose room member is the IRI of the room container.

A client MUST send the request with the credentials it uses for the storage only when [[SOLID-SD]] allows it to send them to that service URL, and otherwise MUST send it without credentials.

The relay answers a ticket request with the first of the following that applies.

When the body is not a JSON object with a string room member holding an absolute IRI, or that IRI is not in a storage the relay serves, the relay MUST respond 400 Bad Request without reading or changing any resource.

When the request carries no credentials, or credentials the storage does not accept, and the public may not read the room in the request's authorization context, the relay MUST respond 401 Unauthorized with a WWW-Authenticate header as the storage would for a read of a protected resource, whether or not a container exists at the room IRI.

When there is no container at the room IRI, or the requesting agent may not read the room container in the request's authorization context, the relay MUST respond 404 Not Found, with the same body and headers in both cases.

When the requesting agent may read the room container but may not read every log resource in it, the relay MUST respond 403 Forbidden.

Otherwise the relay MUST respond 200 OK with an application/json body: a JSON object whose url member is the WebSocket URL to open and whose expires member is the time the ticket stops being accepted, as an [[RFC3339]] date-time with a time zone.

The relay MUST send a ticket response with Cache-Control: no-store.

The relay merges every log resource into one room state and cannot send an agent part of it, so it serves a room only to agents who may read all of it. Unauthenticated requests get the same 401 for a missing room and a protected one, and authenticated ones the same 404, so the ticket endpoint does not reveal whether a container exists to someone who may not read it.

Ticket properties

A ticket MUST carry at least 128 bits from a cryptographically secure random source.

The relay MUST bind a ticket to the room, the requesting agent and the request's authorization context, including the value of its Origin header or the absence of one.

The expires time MUST be no more than 300 seconds after the relay issues the ticket, and SHOULD be no more than 60 seconds after.

A relay MUST accept a ticket for at most one connection, and MUST NOT accept it after its expires time.

The url MUST use the wss scheme and the host and port of the ticket endpoint.

A client MUST NOT open a url whose scheme is not wss or whose host and port differ from those of the ticket endpoint, unless the host is a loopback address the client is configured to trust, in which case the ws scheme is also allowed.

A relay MUST NOT write tickets to logs, and SHOULD carry the ticket in the URL's query component so that infrastructure which logs paths does not record it.

The relay

Opening a connection

A client opens a connection by starting a WebSocket handshake [[RFC6455]] to the ticket's url, unchanged, before the ticket expires.

A client MUST NOT add its storage credentials, such as an access token or a proof of possession, to the WebSocket URL, the handshake's headers or the connection's messages.

A relay MUST authenticate a connection by its ticket alone, and MUST ignore cookies and other credentials a browser attaches to the handshake on its own.

A relay MUST refuse the handshake with 403 Forbidden when the ticket is missing, unknown, expired or already used.

A relay MUST refuse the handshake with 403 Forbidden when its Origin header, or the absence of one, differs from that of the ticket request.

A relay MUST bind each connection to the room, agent and authorization context of its ticket, whatever else the URL's path says.

Before a relay sends the first sync message on a connection, it MUST either complete a load of the room as describes after accepting the connection, or have ingested, as , and require, every change to the room container since its last such load. Content that left the room before the relay read it, and that no log resource holds, is exempt.

A relay that relies on observing the room container MUST start observing before it starts a load, so that no log resource created during the load is missed, and MUST load the room again when it cannot tell whether it missed one.

Messages

Messages are those of the y-websocket protocol [[Y-PROTOCOLS]]. Each message is one binary WebSocket message, whatever frames carry it, laid out as below. varUint is the variable-length unsigned integer, varBytes a varUint length followed by that many bytes, and varString a varBytes holding UTF-8, all as lib0 encodes them.

MessageLayout
sync step 1varUint 0, varUint 0, varBytes state vector
sync step 2varUint 0, varUint 1, varBytes Yjs v1 update
updatevarUint 0, varUint 2, varBytes Yjs v1 update
awareness updatevarUint 1, varBytes awareness update as y-protocols encodes it
permission deniedvarUint 2, varUint 0, varString reason
awareness queryvarUint 3

Clients and relays MUST send each message as one binary WebSocket message laid out as in the table above.

A relay MUST close a connection that sends a text message with status code 1003.

A relay MUST close with status code 1007 a connection that sends a message it cannot decode, or a sync step 2 or update whose payload it cannot apply without error, leaving its room state unchanged.

A relay MAY close a connection that sends a message larger than a limit it chooses, with status code 1009.

A relay MUST process the messages of one connection in the order it receives them.

Once a connection is open and the room is loaded, a relay MUST send a sync step 1 holding the state vector of its room state, and a client SHOULD send a sync step 1 holding its own.

A relay MUST answer each sync step 1 it accepts with a sync step 2 holding the content of its room state that the received state vector lacks.

Authorization of every message

Access to a room can change while a connection is open. The relay checks it for every message it delivers and every update it accepts, against the access control in force when it does so. There is no window after a change during which an earlier decision still applies.

When a relay hands a sync or awareness message to a connection for transmission, it MUST establish that the connection's agent may read the room in the connection's authorization context, taking into account every change to access control that the storage committed before that moment.

When the agent may no longer read the room, the relay MUST NOT send the message, MUST discard every message queued for the connection and not yet transmitted, MUST send a permission-denied message with the reason read, and MUST close the connection with status code 4403.

When a relay processes a sync step 2 or update received on a connection, it MUST establish that the connection's agent may write the room in the connection's authorization context, taking into account every change to access control that the storage committed before that moment.

When the agent may not write the room, the relay MUST NOT apply, persist or forward any part of the message, and MUST send a permission-denied message with the reason write. It MAY keep the connection open for reading.

A relay MUST NOT forward an awareness update received on a connection whose agent may not read the room.

When the room container is deleted, a relay MUST close every connection to the room with status code 4404, discard its room state, and stop accepting tickets issued for the room.

A client that receives a permission-denied message with the reason write MUST stop sending updates on that connection and MUST keep every change it has not treated as stored (), including changes it already sent.

A relay that runs beside the storage server can meet these rules by consulting the storage's access control for each message, or by invalidating cached decisions inside the same transaction that commits an access control change. The moments that count are when the relay processes a received message and when it hands a message to the connection, not when bytes reach the network. A relay that learns of changes through notifications sent after the commit does not meet them.

Persistence

The relay is a writer and reader of the room's log like any client. What it accepts from connections becomes update resources, and what clients write as resources reaches the connections.

A relay MUST persist the content that each accepted sync step 2 or update adds to its room state as update resources in the room container.

A relay MAY persist the content of several accepted messages as one update resource.

A relay MUST NOT send content accepted from one connection to any other connection before the creation of an update resource holding it is confirmed.

Once the creation of an update resource holding content accepted from one connection is confirmed, a relay MUST send that content to every other connection of the room, subject to .

A relay MUST NOT send a sync step 2 answering a sync step 1 until every part of its room state at the moment it processed that sync step 1, and all content it accepted from that connection before that sync step 1, is held by a log resource whose creation is confirmed, whichever connection the content came from.

A relay MUST keep the content it accepted that no log resource with confirmed creation holds yet until one does, MUST keep it across any rebuild of its room state, and MUST apply it to the rebuilt room state.

A relay MUST answer the sync step 1 messages it receives on a connection in the order it received them, with one sync step 2 each.

A relay MUST NOT create update resources for content that it added to its room state by reading the room's log resources; it persists only what accepted messages add (), even when a resource it once read held the same content. Snapshot resources it creates as a compactor are not affected.

A relay MUST NOT give a log resource it creates access control of its own; it is governed by the room container's access control.

While a room has open connections, a relay MUST apply to its room state the content of every log resource that another writer creates in the room container or moves into it, either from that resource or from a log resource that holds its content, and deliver the content it adds to the connections, subject to . Content that left the room before the relay read it, and that no log resource holds, is exempt.

When a resource the relay learned of is gone when read, or the relay cannot tell whether it missed a change to the room container, the relay MUST catch up from a complete listing as describes.

When a log resource leaves the room other than by the relay's own compaction, the relay MUST rebuild its room state by loading the room, and applying the content kept under , before it next delivers content to a connection.

Deleting a log resource does not remove its content from a document: clients that hold the content send it again, and the relay persists it. Content is removed by editing the document, which Yjs records as a deletion. Rebuilding the room state after a removal keeps the relay from serving content that no log resource holds and no client sends.

A relay SHOULD deliver the content of a log resource that another writer creates in the room within five seconds of its creation.

A relay MUST NOT apply a resource that is not a valid log record or a supported legacy update resource, and MUST NOT close connections because of one.

Awareness

Awareness carries presence: who is in the room, their cursor and selection, and whatever other state the application shares. It is never stored.

A relay MUST forward each awareness update it accepts to the other connections of the room, subject to .

Clients and relays MUST NOT persist awareness state in the room.

When a connection closes, a relay SHOULD send the other connections of the room an awareness update that removes the closed connection's awareness states.

Client durability

The y-websocket protocol has no acknowledgement. A client knows its changes are stored when the relay answers a sync step 1 the client sent after sending them, because of . A client that opens a connection sends a sync step 1 at once, so the answer to that first sync step 1 confirms nothing the client sent after it.

A client MUST treat a change it sent to a relay as stored only after it has received a sync step 2 answering a sync step 1 that it sent, on the same connection, after every message carrying the change, with no permission-denied message between sending the change and receiving that sync step 2. A client matches each sync step 2 it receives to the earliest sync step 1 it sent on that connection that has no answer yet.

A client that holds changes not yet treated as stored and whose connection closed MUST, before it discards them, either complete that exchange on a new connection or write them as an update resource ().

A client can compute the changes to write as the update between its room state and the last state vector the relay confirmed. Writing a change the relay already stored only duplicates it, which is harmless.

Discovery

A storage server that offers a relay MUST list it in the storage description as a ssd:CrdtSyncService whose service endpoint is the ticket endpoint and whose dcterms:conformsTo includes ssd:y-protocol-v1 [[SOLID-SD]].

A relay listed for a storage MUST accept every container in that storage as a room.

The ssd:roomTemplate property of [[SOLID-SD]] is informative under this profile: clients open the URL a ticket gives them and never build one from the template.

A client that finds no relay conforming to this profile, or cannot reach one, MAY still edit a room by writing and reading log resources as describes.

Security considerations

A ticket is a bearer secret for one connection to one room. It is short-lived and single-use, it never travels to another origin, and it grants nothing the agent could not already read. Because the relay authorizes every message against current access control, a stolen ticket used before its owner does gives the thief at most the owner's current access to that room, and revoking the owner's access ends it.

Access control applies to a room as a whole (). A storage that lets agents set access control on individual resources cannot stop a client that ignores from doing so; the relay then refuses tickets to agents who cannot read every log resource, and compactors that can see such access control leave those resources alone.

Log resources and relayed messages come from other agents and may be hostile. Readers check every payload decodes before applying it, cap the bytes they read for one resource and for a listing, and reject redirects on credentialed requests as [[SOLID-SD]] requires. A writer with access to a room can make the document arbitrarily large; storages can apply quotas to room containers as to any other.

Cross-site WebSocket hijacking relies on credentials a browser attaches on its own. Relays authenticate connections by ticket only and require the handshake's Origin to match the ticket request's (), so a page on another site cannot open a connection on a user's behalf, nor use another application's ticket to act with that application's permissions.

Privacy considerations

Awareness reveals who has a document open and where they are working in it, to every agent who may read the room. Applications should tell users when their presence is shared. The relay sees every update in plain form, as the storage does.

Test vectors

The directory vectors/ holds a manifest of cases. Each case lists resources by name with their bodies in hexadecimal and states either the expected document content after loading them, or that a named resource is not a valid log record. The cases cover the header layout, update and snapshot records, a snapshot that does not hold an update written earlier offline, legacy resources, and invalid bodies. They are generated with a pinned version of Yjs, and tools/spec-check checks them in the repository gate.

Implementation status

@jeswr/y-solid 0.1 implements the update log without headers (the legacy form) and compacts by writing a merged update and deleting exactly what it merged. It does not yet write headers, list again when a resource vanishes during a load, or delete with If-Match. The suite's re-platformed provider (ADR-006 of the suite plan) adopts this profile. No relay implements it yet; sparq tracks one.
