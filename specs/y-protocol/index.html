This specification defines y-protocol-v1, the profile of the Solid Storage Service Description's CRDT sync service for documents edited with Yjs. A Yjs document lives in a container of a Solid or Linked Web Storage storage as a log of update resources. Clients without a relay collaborate by writing and reading those resources. A relay adds real-time exchange and presence over WebSocket: clients obtain a short-lived ticket, the relay authorizes every message it delivers or accepts against the storage's access control at that moment, persists what it accepts into the same container, and passes on what other clients write there. The specification fixes the byte layout of the stored resources, the rules for loading and compacting the log without losing updates, and the ticket exchange.

This is an unofficial personal draft. It is not a work item of the W3C Solid Community Group or of any W3C Working Group, and its identifier is minted under a personal namespace until a venue adopts it. It completes the ssd:CrdtSyncService entry of [[SOLID-SD]], which names this profile and leaves its protocol to this document.

This draft was prepared with the assistance of AI systems operated on behalf of the editor (drafting: Claude Opus 5.5). The editor is responsible for all content. Issues are welcome on the GitHub repository.

Introduction

Motivation

Collaborative editors such as the suite's Docs, Sheets and Notes keep their documents as Yjs documents. A Yjs document is a set of updates: applying the same updates in any order, any number of times, gives the same document. That property lets a document live in a storage as a container of small, write-once resources, one per update, which any client with access can append to without a read-modify-write race.

A log of resources gives eventual consistency with latency of seconds and no presence. A relay gives both, but a relay that only checks access when a connection opens keeps sending a document to someone whose access was revoked, and a relay that keeps its own copy of the document splits it from the log. This profile ties the two together: one storage encoding, one loading rule, one compaction rule, and a relay that is a reader and writer of the same log, bound to the storage's access control for every message.

Overview

A storage that offers a relay lists a ssd:CrdtSyncService whose dcterms:conformsTo names this profile, with the ticket endpoint as its service endpoint [[SOLID-SD]]. 

<https://pod.example/> did:service
    [ a ssd:CrdtSyncService ;
      did:serviceEndpoint <https://pod.example/.sync/tickets> ;
      dct:conformsTo ssd:y-protocol-v1 ] .

A client that edits the document in the container https://pod.example/docs/plan/:

  1. loads the document by reading every update and snapshot resource in the container ();
  2. requests a ticket by sending {"room": "https://pod.example/docs/plan/"} to the ticket endpoint with its storage credentials, and receives a WebSocket URL and an expiry ();
  3. opens the WebSocket and exchanges Yjs sync and awareness messages with the relay ();
  4. without a relay, or while disconnected from it, writes each change as a new update resource in the container ().

This specification defines three conformance classes. A relay is the server component behind a ssd:CrdtSyncService that conforms to this profile. A client is software that reads or edits a room, with or without a relay. A compactor is a client or relay that compacts a room; it meets the requirements on its own class and those of .

The machine-readable list of this specification's normative statements is the companion document spec.statements.ttl. The test vectors in vectors/ are normative for the byte layout and the loading rule: where the prose and a vector disagree, report it as an issue. Examples are informative.

Terminology

This specification uses the terms storage, storage server, service, service endpoint and service URL as [[SOLID-SD]] defines them, and the terms update, state vector and client ID as [[YJS]] defines them.

room
A container in a storage that holds one Yjs document as a log of update and snapshot resources. The container's IRI identifies the room and the document.
update resource
A non-container resource in a room whose body is a JYU1 record ().
snapshot resource
A non-container resource in a room whose body is a JYS1 record: an update that holds the content of other update and snapshot resources it replaced.
log resource
An update resource, a snapshot resource or a legacy update resource ().
room state
The Yjs document a client or relay holds for a room.
connection
A WebSocket connection between a client and a relay, opened with a ticket, bound to one room and one agent.
may read the room
An agent may read the room when the storage's access control lets it read the room container and every log resource in it.
may write the room
An agent may write the room when it may read the room and the storage's access control lets it create resources in the room container (in Web Access Control [[WAC]], acl:Append or acl:Write on the container).

The profile IRI is https://jeswr.org/ns/solid-sd#y-protocol-v1, written ssd:y-protocol-v1.

Storage encoding

A log resource body is a 16-byte header followed by a Yjs update. The header lets a reader tell an update from a snapshot and order resources without relying on their names, which a Linked Web Storage server chooses.

BytesFieldContent
0–3magic4A 59 55 31 (ASCII JYU1) for an update, 4A 59 53 31 (ASCII JYS1) for a snapshot
4–11timeunsigned 64-bit big-endian integer: milliseconds since 1970-01-01T00:00:00Z when the writer created the record
12–15nonce4 bytes chosen at random by the writer
16–endpayloada Yjs update in the v1 update encoding [[YJS]]

A client or relay that writes a log resource MUST write a body laid out as in the table above, with a payload that decodes without error as a Yjs update in the v1 update encoding.

The time field MUST NOT exceed 253 − 1.

A writer MUST draw the nonce from a cryptographically secure random source.

A reader MUST treat a body as a valid log record only when it is at least 16 bytes long, begins with one of the two magic values, has a time field no greater than 253 − 1, and has a payload that decodes without error as a Yjs update in the v1 update encoding.

The ordering key of a log resource is the triple (time, nonce read as an unsigned 32-bit big-endian integer, resource IRI compared by code point). Yjs gives the same document in any order of application; the key only makes loading deterministic.

A writer MUST create log resources with the media type application/octet-stream.

A reader MUST decide whether a resource is a log resource from its body, not from its media type or its name.

No client or relay may change the body of a log resource after it is created: a writer MUST NOT send a PUT or PATCH request to an existing log resource.

Legacy update resources

Version 0.1 of @jeswr/y-solid writes each update with no header, as a resource named with a 15-digit zero-padded millisecond time, a hyphen and a UUID, for example 001761480000000-0f8e2c6a-3b1d-4f5e-9a7c-2d4b6e8f0a1c. Rooms it wrote can be read under this profile.

A legacy update resource is a non-container resource in a room whose body does not begin with either magic value, whose last path segment matches ^[0-9]{15}-[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$, and whose whole body decodes without error as a Yjs update in the v1 update encoding. Its ordering key is (the 15-digit time, 0, resource IRI).

A reader SHOULD apply legacy update resources as it applies update resources.

A writer MUST NOT create a legacy update resource.

A Yjs v1 update whose first four bytes equal a magic value would have to hold structures for 74 clients, the first with 89 structures and client ID 85; Yjs draws client IDs at random from 232 values, so a legacy update is not mistaken for a headed one in practice.

The update log

Writing updates

A client that writes a change to a room without a relay MUST create a new update resource in the room container whose payload holds the change, using a request that cannot replace an existing resource: POST to the container, or PUT with If-None-Match: *.

A writer that suggests a name for a log resource MUST include at least 32 random bits in it.

Names such as 01761480000000-k3v9q2xa.yupdate and snapshot-01761480000000-p8m2w7cd.ysnap (13-digit time, eight base32 characters) are a convenient choice. Unique names, conditional creation and conditional deletion together keep a resource's IRI from ever naming two different records, which compaction relies on.

A client or relay MUST NOT create a container inside a room.

Loading a room

A client or relay loads a room by listing the room container, reading each log resource it lists and applying the payloads to its room state.

A reader MUST apply every valid update resource, every valid snapshot resource and, when it supports them, every legacy update resource that it reads in the room, and MUST NOT leave one out because of its time, its name, or the presence of a snapshot resource with a later time.

A reader MUST NOT apply any part of a resource in a room that is not a valid log record or a legacy update resource it supports, and SHOULD report it.

A reader MUST check that a payload decodes without error before applying any of it to its room state.

When a resource that a listing named is gone when read (404 Not Found or 410 Gone), a reader MUST list the room container again and read every log resource in the new listing that it has not yet read, before it treats the room as loaded.

A reader MAY stop after a number of listings of its choosing, but MUST then report that the load did not complete and MUST NOT report the room as loaded.

A reader SHOULD apply log resources in ascending order of their ordering keys.

A reader MUST ignore containers inside a room.

A resource gone between listing and reading was deleted by a compactor after its content was written to a new snapshot resource (), so the next listing names that snapshot. Reading it again is harmless because applying an update twice changes nothing.

Watching a room without a relay

A client may subscribe to notifications on the room container [[SOLID-NOTIFICATIONS]] and read each log resource reported as created. This gives eventual consistency within seconds, with no presence.

A client that relies on notifications to learn of new log resources MUST load the room again whenever it cannot tell whether it missed a notification, such as after its subscription lapsed or its channel reconnected.

Compaction

A room grows by one resource per write. A compactor replaces a set of log resources with one snapshot resource that holds their content, then deletes them. Several compactors may work on a room at once, offline or online; the rules below keep every update in some resource at every moment, whatever their interleaving.

A compactor that compacts a set R of log resources MUST first create a snapshot resource whose payload is a Yjs update containing the content of every resource in R, using a request that cannot replace an existing resource.

A compactor MUST NOT delete a resource in R until the storage has answered the creation of that snapshot resource with a 2xx status.

A compactor MUST NOT delete a resource unless it read the whole body of that resource, found it to be a valid log record or a legacy update resource, and applied it to the room state from which it built the snapshot.

When the compactor's room state holds content that Yjs has not yet integrated because it depends on updates the compactor has not seen, the snapshot payload MUST include that content, or the compactor MUST NOT delete the resources that carried it.

A compactor MUST send each deletion with an If-Match header carrying the entity tag it received when it read that resource, when it received one, and MUST NOT delete a resource for which it received none unless the resource's IRI includes at least 32 random bits.

A compactor MUST treat a 404 Not Found or 410 Gone answer to a deletion as success, and a 412 Precondition Failed answer as a resource it must leave in place.

A client MUST NOT compact a room that it may not write.

Every deleted resource's content is in a snapshot resource that existed before the deletion. A later compactor that deletes that snapshot has, by the same rules, first written a newer snapshot holding it. Two compactors that read overlapping sets each write a snapshot holding everything they read, so a resource deleted by one is still held by the other's snapshot or by the first one's. A loader that reads every log resource therefore always sees every update. Compaction removes history: a storage that offers a versioning service keeps earlier versions as [[SOLID-SD]] describes.

Tickets

The relay speaks WebSocket, and browsers cannot attach the storage's credentials to a WebSocket handshake. A client therefore exchanges its credentials for a ticket over HTTP first. The ticket endpoint is the service endpoint of the ssd:CrdtSyncService.

Requesting a ticket

A client requests a ticket by sending a POST request to the ticket endpoint with an application/json body: a JSON object whose room member is the IRI of the room container.

A client MUST send the request with the credentials it uses for the storage only when [[SOLID-SD]] allows it to send them to that service URL, and otherwise MUST send it without credentials.

When the room member names a container in a storage the relay serves, and the requesting agent may read the room, the relay MUST respond 200 OK with an application/json body: a JSON object whose url member is the WebSocket URL to open and whose expires member is the time the ticket stops being accepted, as an [[RFC3339]] date-time with a time zone.

The relay MUST send a ticket response with Cache-Control: no-store.

The relay MUST respond 400 Bad Request, without reading or changing any resource, when the body is not a JSON object with a string room member holding an absolute IRI, or when that IRI is not in a storage the relay serves.

When the request carries no credentials, or credentials the storage does not accept, and the public may not read the room, the relay MUST respond 401 Unauthorized with a WWW-Authenticate header as the storage would for a read of the room container.

When there is no container at the room IRI, or the authenticated agent may not read the room container, the relay MUST respond 404 Not Found, with the same body and headers in both cases.

When the authenticated agent may read the room container but may not read every log resource in it, the relay MUST respond 403 Forbidden.

The relay merges every log resource into one room state and cannot send an agent part of it, so it serves a room only to agents who may read all of it. The 404 answer covers both a missing room and an unreadable one, so the ticket endpoint does not reveal whether a container exists to someone who may not read it.

Ticket properties

A ticket MUST carry at least 128 bits from a cryptographically secure random source, and the relay MUST bind it to the room and to the agent that requested it.

The expires time MUST be no more than 300 seconds after the relay issues the ticket, and SHOULD be no more than 60 seconds after.

A relay MUST accept a ticket for at most one connection, and MUST NOT accept it after its expires time.

The url MUST use the wss scheme and the host and port of the ticket endpoint.

A client MUST NOT open a url whose scheme is not wss or whose host and port differ from those of the ticket endpoint, unless the host is a loopback address the client is configured to trust, in which case the ws scheme is also allowed.

A relay MUST NOT write tickets to logs, and SHOULD carry the ticket in the URL's query component so that infrastructure which logs paths does not record it.

The relay

Opening a connection

A client opens a connection by starting a WebSocket handshake [[RFC6455]] to the ticket's url, unchanged, before the ticket expires.

A client MUST NOT send its storage credentials on the WebSocket handshake or over the connection.

A relay MUST authenticate a connection by its ticket alone, and MUST NOT accept cookies or other credentials the browser attaches on its own as a substitute.

A relay MUST refuse the handshake with 401 Unauthorized when the ticket is missing, unknown, expired or already used.

A relay MUST bind each connection to the room and agent of its ticket, whatever else the URL's path says.

A relay MUST NOT send a sync message on a connection until it has loaded the room as describes.

Messages

Messages are those of the y-websocket protocol [[Y-PROTOCOLS]]. Each WebSocket message is one binary frame holding a variable-length unsigned integer message type followed by the message for that type: 0 for a sync message (sync step 1, sync step 2 or update), 1 for an awareness update, 2 for an auth message, 3 for an awareness query.

Clients and relays MUST send messages as binary frames encoded as [[Y-PROTOCOLS]] defines.

A relay MUST close a connection that sends a text frame with status code 1003.

A relay MUST close a connection that sends a message it cannot decode, or a sync update that does not decode as a Yjs update, with status code 1007, without applying any part of it.

A relay MAY close a connection that sends a message larger than a limit it chooses, with status code 1009.

A relay MUST process the messages of one connection in the order it receives them.

Once a connection is open and the room is loaded, a relay MUST send a sync step 1 holding the state vector of its room state, and a client SHOULD send a sync step 1 holding its own.

A relay MUST answer each sync step 1 it accepts with a sync step 2 holding the content of its room state that the received state vector lacks.

Authorization of every message

Access to a room can change while a connection is open. The relay checks it for every message it delivers and every update it accepts, against the access control in force when it does so. There is no window after a change during which an earlier decision still applies.

Before a relay sends a sync or awareness message on a connection, it MUST establish that the connection's agent may read the room, taking into account every change to access control that the storage committed before the message is sent.

When the agent may no longer read the room, the relay MUST NOT send the message, MUST send an auth message of type permission-denied with the reason read, and MUST close the connection with status code 4403.

When a relay receives a sync step 2 or update on a connection, it MUST establish that the connection's agent may write the room, taking into account every change to access control that the storage committed before the relay received the message.

When the agent may not write the room, the relay MUST NOT apply, persist or forward any part of the message, and MUST send an auth message of type permission-denied with the reason write. It MAY keep the connection open for reading.

A relay MUST NOT forward an awareness update received on a connection whose agent may not read the room.

When the room container is deleted, a relay MUST close every connection to the room with status code 4404.

A client that receives a permission-denied auth message with the reason write MUST stop sending updates on that connection and MUST keep its unsent changes.

A relay that runs beside the storage server can meet these rules by consulting the storage's access control for each message, or by invalidating cached decisions inside the same transaction that commits an access control change. A relay that learns of changes through notifications sent after the commit does not meet them.

Persistence

The relay is a writer and reader of the room's log like any client. What it accepts from connections becomes update resources, and what clients write as resources reaches the connections.

A relay MUST persist the content that each accepted sync step 2 or update adds to its room state as update resources in the room container.

A relay MAY persist the content of several accepted messages as one update resource.

A relay MUST NOT send content accepted from one connection to any other connection before the storage has answered the creation of an update resource holding it with a 2xx status.

A relay MUST NOT send a sync step 2 answering a sync step 1 received on a connection until every update resource holding content it accepted from that connection before that sync step 1 has been created.

A relay MUST NOT persist content that it read from the room's log resources.

A relay MUST NOT give a log resource it creates access control of its own; it is governed by the room container's access control.

While a room has open connections, a relay MUST apply to its room state every log resource created in the room container by any other writer, and deliver the content it adds to the connections, subject to .

A relay SHOULD deliver the content of such a log resource within five seconds of its creation.

A relay MUST NOT apply a resource that is not a valid log record or a supported legacy update resource, and MUST NOT close connections because of one.

Awareness

Awareness carries presence: who is in the room, their cursor and selection, and whatever other state the application shares. It is never stored.

A relay MUST forward each awareness update it accepts to the other connections of the room, subject to .

Clients and relays MUST NOT persist awareness state in the room.

When a connection closes, a relay SHOULD send the other connections of the room an awareness update that removes the closed connection's awareness states.

Client durability

The y-websocket protocol has no acknowledgement. A client knows its changes are stored when the relay answers a sync step 1 the client sent after making them, because of .

A client MUST treat a change it sent to a relay as stored only after it has received a sync step 2 answering a sync step 1 that it sent after the change, on the same connection.

A client that holds changes not yet treated as stored and whose connection closed MUST, before it discards them, either complete that exchange on a new connection or write them as an update resource ().

A client can compute the changes to write as the update between its room state and the last state vector the relay confirmed. Writing a change the relay already stored only duplicates it, which is harmless.

Discovery

A storage server that offers a relay MUST list it in the storage description as a ssd:CrdtSyncService whose service endpoint is the ticket endpoint and whose dcterms:conformsTo includes ssd:y-protocol-v1 [[SOLID-SD]].

A relay listed for a storage MUST accept every container in that storage as a room.

The ssd:roomTemplate property of [[SOLID-SD]] is informative under this profile: clients open the URL a ticket gives them and never build one from the template.

A client that finds no relay conforming to this profile, or cannot reach one, MAY still edit a room by writing and reading log resources as describes.

Security considerations

A ticket is a bearer secret for one connection to one room. It is short-lived and single-use, it never travels to another origin, and it grants nothing the agent could not already read. Because the relay authorizes every message against current access control, a stolen ticket used before its owner does gives the thief at most the owner's current access to that room, and revoking the owner's access ends it.

A relay holding the merged room state can only serve agents who may read every log resource. Storages and clients should not give individual log resources access control that differs from the room container's; the relay never does ().

Log resources and relayed messages come from other agents and may be hostile. Readers check every payload decodes before applying it, cap the bytes they read for one resource and for a listing, and reject redirects on credentialed requests as [[SOLID-SD]] requires. A writer with access to a room can make the document arbitrarily large; storages can apply quotas to room containers as to any other.

Cross-site WebSocket hijacking relies on credentials a browser attaches on its own. Relays authenticate connections by ticket only (), so a page on another site cannot open a connection on a user's behalf without a ticket.

Privacy considerations

Awareness reveals who has a document open and where they are working in it, to every agent who may read the room. Applications should tell users when their presence is shared. The relay sees every update in plain form, as the storage does.

Test vectors

The directory vectors/ holds a manifest of cases. Each case lists resources by name with their bodies in hexadecimal and states either the expected document content after loading them, or that a named resource is not a valid log record. The cases cover the header layout, update and snapshot records, a snapshot that does not hold an update written earlier offline, legacy resources, and invalid bodies. They are generated with a pinned version of Yjs, and tools/spec-check checks them in the repository gate.

Implementation status

@jeswr/y-solid 0.1 implements the update log without headers (the legacy form) and compacts by writing a merged update and deleting exactly what it merged. It does not yet write headers, list again when a resource vanishes during a load, or delete with If-Match. The suite's re-platformed provider (ADR-006 of the suite plan) adopts this profile. No relay implements it yet; sparq tracks one.
