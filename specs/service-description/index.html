This specification lets a Solid storage describe the services and capabilities it offers, such as notifications, server-side query, real-time collaboration, version history, trash, patch formats and its access control model, in its existing storage description resource. The description uses RDF terms that map one to one onto the service and capability entries of a Linked Web Storage storage description [[LWS-CORE]], so a single client parser serves storages of both protocols, and a Solid storage can serve a description that is also a valid Linked Web Storage storage description.

This is an unofficial personal draft. It is not a work item of the W3C Solid Community Group or of any W3C Working Group, and its terms are minted under a personal namespace until a venue adopts it. It is written to inform the open Solid Protocol discussions on server and capability discovery (solid/specification issues 355, 699, 455 and 804) and the Linked Web Storage discussion of Solid compatibility.

This draft was prepared with the assistance of AI systems operated on behalf of the editor (drafting: Claude Opus 5.5). The editor is responsible for all content. Issues are welcome on the GitHub repository.

Introduction

Motivation

The Solid Protocol [[SOLID-PROTOCOL]] gives every storage a storage description resource, found through a Link header with the relation http://www.w3.org/ns/solid/terms#storageDescription. Today the only thing that resource has to say is that the storage is a pim:Storage. The Solid Notifications Protocol [[SOLID-NOTIFICATIONS]] adds subscription services to it, and the access-controlled query draft [[ACQ]] adds a query endpoint, but everything else a client wants to know (which access control model to write, which patch formats work, whether deleting a folder needs a recursive walk) it learns by probing headers resource by resource, or not at all.

Linked Web Storage [[LWS-CORE]] solved the same problem with one document: the storage description lists service entries (a type and an endpoint) and capability entries (a type and parameters), and clients ignore types they do not know. This specification lets a Solid storage say the same things, in RDF, at the place it already describes itself. It defines no new discovery mechanism and changes nothing a client that ignores it relies on.

Design goals

  • One parser for both protocols. The RDF graph a Solid storage serves has the same shape as the graph a Linked Web Storage description means under its JSON-LD context, with the same property IRIs.
  • Reuse before minting. Terms Linked Web Storage, the Controlled Identifier vocabulary, Solid Notifications and the access-controlled query draft already define are used by IRI. This specification mints only the service and capability types that have no existing term.
  • Must-ignore extensibility. Any party can add a service or capability type. Clients ignore what they do not understand, so adding an entry never breaks a client.
  • Advisory, never authoritative. The description tells a client what to try. It never grants access and never replaces the authorization decision on each request.

Example

A storage at https://pod.example/ that offers WebSocket notifications, an access-controlled SPARQL endpoint, a Yjs sync relay and N3 Patch on Turtle resources, and enforces Web Access Control, describes itself as follows. 

@prefix pim:    <http://www.w3.org/ns/pim/space#> .
@prefix lws:    <https://www.w3.org/ns/lws#> .
@prefix did:    <https://www.w3.org/ns/did#> .
@prefix notify: <http://www.w3.org/ns/solid/notifications#> .
@prefix dct:    <http://purl.org/dc/terms/> .
@prefix ssd:    <https://jeswr.org/ns/solid-sd#> .

<https://pod.example/> a pim:Storage, lws:Storage ;
  did:service
    [ a lws:StorageRoot ;
      did:serviceEndpoint <https://pod.example/> ] ,
    [ a ssd:SolidNotificationService ;
      did:serviceEndpoint <https://pod.example/.notifications/WebSocketChannel2023/> ;
      notify:channelType notify:WebSocketChannel2023 ] ,
    [ a ssd:SparqlQueryService ;
      did:serviceEndpoint <https://pod.example/sparql> ;
      dct:conformsTo <https://jeswr.github.io/solid-specs/specs/access-controlled-query/> ] ,
    [ a ssd:CrdtSyncService ;
      did:serviceEndpoint <https://pod.example/.sync/tickets> ;
      dct:conformsTo ssd:y-protocol-v1 ] ,
    [ a ssd:RecursiveDeleteService ;
      did:serviceEndpoint <https://pod.example/.delete> ] ;
  lws:capability
    [ a ssd:AccessControl ; ssd:model ssd:WAC ] ,
    [ a ssd:PatchSupport ;
      ssd:source "text/turtle" ;
      ssd:patchType "text/n3", "application/sparql-update" ] .

This specification defines two conformance classes. A storage server is a server that hosts one or more Solid storages and serves their storage description resources. A client is software that reads a storage description to decide how to interact with a storage.

The machine-readable list of this specification's normative statements is the companion document spec.statements.ttl. The SHACL shapes in shapes/solid-sd.ttl, the vocabulary in vocab/solid-sd.ttl and the JSON-LD context in context/v1.jsonld are normative. Examples are informative.

Terminology

This specification uses the following terms.

storage
A storage as defined by the Solid Protocol [[SOLID-PROTOCOL]]: a space of URIs rooted at a container typed pim:Storage.
storage root
The root container of a storage. Its IRI identifies the storage.
storage description resource
The resource a storage server links to from resources in a storage with the relation http://www.w3.org/ns/solid/terms#storageDescription [[SOLID-PROTOCOL]].
service
A network interface connected to a storage, described by a type and a service endpoint, with the semantics of a service in a Controlled Identifier document [[CID]].
service endpoint
The IRI at which a client starts interacting with a service.
capability
A behaviour of the storage's own resource operations, described by a type and optional parameters, with the semantics of a capability in a Linked Web Storage storage description [[LWS-CORE]].
entry
A service or a capability in a storage description.
profile
A specification that pins the protocol a service speaks, named by dcterms:conformsTo.

Location and representation

The storage description resource

This specification adds statements to the storage description resource the Solid Protocol already defines. It does not change how that resource is found.

A storage server that describes services or capabilities of a storage MUST do so in the storage description resource of that storage.

The subject of every did:service and lws:capability statement in a storage description resource MUST be the IRI of the storage root.

A storage server SHOULD type the storage root lws:Storage in addition to pim:Storage.

The service and capability statements of a storage description resource MUST NOT vary with the identity of the requester.

Representations

A storage server MUST serve the storage description resource as text/turtle when the request prefers it.

A storage server MUST serve the storage description resource as application/ld+json when the request prefers it.

A JSON-LD representation that uses the context defined by this specification MUST list https://www.w3.org/ns/cid/v1, then https://www.w3.org/ns/lws/v1, then that context, before any other context.

The context's IRI is https://jeswr.org/ns/solid-sd/context/v1. Its content is context/v1.jsonld. It defines no term that the Controlled Identifier or Linked Web Storage contexts define, so it never redefines a protected term.

A storage server MAY embed the content of this specification's context inline instead of referencing its IRI.

A storage server MAY also serve the storage description resource as application/lws+cid.

An application/lws+cid representation of a storage description resource MUST satisfy the storage description requirements of [[LWS-CORE]].

All representations of a storage description resource MUST express the same service and capability statements.

With these rules a Solid storage can be discovered by a Linked Web Storage client through the description alone: the same graph, serialised with the Controlled Identifier and Linked Web Storage contexts first, is a Linked Web Storage storage description. Whether the storage also emits the Linked Web Storage storage link relation is outside this specification.

The Linked Web Storage context https://www.w3.org/ns/lws/v1 is not yet published. This specification assumes it defines no global source, target, model or patchType term. If it does, the extension terms here are renamed before this draft is offered to a venue.

Data model

Services

A storage lists each service as the object of did:service. The service node carries its types and its endpoint.

A service node MUST have at least one rdf:type.

A service node MUST have exactly one did:serviceEndpoint whose value is an IRI.

A storage description that lists any service or capability MUST include a service of type lws:StorageRoot whose endpoint is the storage root.

The lws:StorageRoot service is redundant on Solid, where the storage root is the subject, but it makes the graph a valid Linked Web Storage description and lets one client code path find the root.

Capabilities

A storage lists each capability as the object of lws:capability. A capability describes how the storage's ordinary resource operations behave, so it has no endpoint.

A capability node MUST have at least one rdf:type.

Identifying entries

A service or capability node MAY be an IRI or a blank node.

A storage server SHOULD identify a service node by an IRI that is the storage description resource's IRI or the storage root's IRI with a fragment.

Stable entry IRIs let other documents, such as access grants or audit records, point at a particular service.

Profiles and versions

A service type names what kind of service it is. The protocol it speaks, and that protocol's version, is a profile, named with dcterms:conformsTo. A new version of a service's protocol is a new profile IRI, not a new service type.

Every value of ssd:source, ssd:patchType and ssd:target MUST be a media type of the form type/subtype, without parameters.

The value of dcterms:conformsTo on an entry MUST be an IRI.

An entry MAY list more than one profile when its endpoint speaks each of them.

Extensibility

Any party MAY define new service and capability types.

Every type of a service or capability entry MUST be an absolute IRI.

A service or capability type that this specification or [[LWS-CORE]] does not define MUST be in a namespace its definer controls.

An entry MAY carry properties beyond those its type definition names.

Service types

Linked Web Storage service types

A Solid storage that offers a service Linked Web Storage already defines describes it with the Linked Web Storage type. This specification adds no requirement to these services beyond those of [[LWS-CORE]] and [[LWS-INDEX]].

TypeEndpoint
lws:StorageRootThe storage root.
lws:NotificationServiceA Linked Web Storage subscription endpoint, with lws:subscriptionType.
lws:TypeIndexService, lws:TypeSearchService A server-managed type index and type search [[LWS-INDEX]].
lws:AccessRequestService, lws:AccessGrantService Access request and grant containers, with the access profile as dcterms:conformsTo.

A storage server MUST NOT describe a service that one of these Linked Web Storage types covers with a different type IRI.

Solid notification service

ssd:SolidNotificationService is a subscription service of the Solid Notifications Protocol [[SOLID-NOTIFICATIONS]]. It brings the subscription services a storage already lists with notify:subscription into the did:service list, so a client that reads services finds them in one place.

The endpoint of a ssd:SolidNotificationService MUST be the IRI of a subscription service.

A ssd:SolidNotificationService node MUST have exactly one notify:channelType.

A ssd:SolidNotificationService node MAY have notify:feature values with the meaning the Solid Notifications Protocol gives them.

A storage server that lists a subscription service with notify:subscription SHOULD also list it as a ssd:SolidNotificationService.

The two forms describe the same thing and may share a node: the subscription service IRI can be both the object of notify:subscription and a service node whose endpoint is itself.

SPARQL query service

ssd:SparqlQueryService is a read-only SPARQL query service over the storage. The access-controlled query draft [[ACQ]] already lets a storage name its query endpoint with solid-sparql:endpoint; this type lists the same endpoint as a service.

A ssd:SparqlQueryService node MUST have a dcterms:conformsTo naming the query protocol profile its endpoint implements.

A ssd:SparqlQueryService whose endpoint implements [[ACQ]] MUST list https://jeswr.github.io/solid-specs/specs/access-controlled-query/ as a profile.

A storage server that names an endpoint with solid-sparql:endpoint SHOULD also list it as a ssd:SparqlQueryService.

CRDT sync service

ssd:CrdtSyncService is a real-time relay for collaborative documents kept in the storage as conflict-free replicated data types. Clients that find no such service can still collaborate by writing updates as ordinary resources and watching for notifications; the service adds low latency and presence.

A ssd:CrdtSyncService node MUST have a dcterms:conformsTo naming its sync profile.

The suite's Yjs relay is identified by the profile IRI ssd:y-protocol-v1. This draft names that IRI so descriptions can list it; the profile itself (tickets, rooms, authorization of each delivered update, and the storage encoding shared with clients that write updates as ordinary resources) is specified in a separate draft.

An earlier version of this draft carried the profile as an appendix. Review showed that it needs more than an appendix can hold: serialized or merging compaction so concurrent compactors cannot drop updates, authorization of every relayed update rather than only at connection time, two-way exchange between the relay and the update resources in the room container, and a byte-level encoding with test vectors. It moves to its own draft.

A ssd:CrdtSyncService node MAY have one ssd:roomTemplate, an informative URI template for room URLs.

Recursive delete service

The Solid Protocol refuses a DELETE request on a container that is not empty, so a client deleting a folder walks it and deletes each resource. A ssd:RecursiveDeleteService deletes a container and everything beneath it in one request, leaving the behaviour of DELETE unchanged.

When a client sends a POST request to a recursive delete service endpoint with an application/json body whose container member is the IRI of a container in the storage, and the client may delete the container and every resource beneath it, the storage server MUST delete them all and respond 204 No Content.

A storage server MUST refuse a recursive delete of a container outside the storage with 400 Bad Request, without reading or changing that container.

A storage server MUST refuse a recursive delete that the client is not permitted to make, deleting nothing and responding 403 Forbidden when the client may read the container and 404 Not Found otherwise.

When a recursive delete cannot delete every resource beneath the container, the storage server MUST NOT delete the container.

Versioning service

ssd:VersioningService says the storage keeps immutable prior versions of resources. The versions of a resource are found from the resource itself.

A storage server that lists a ssd:VersioningService MUST include, in successful responses to GET and HEAD requests on each versioned resource, a Link header with the relation version-history whose target is a container listing that resource's versions.

A storage server MUST reject requests that modify a version resource.

A storage server MUST include a Memento-Datetime header in successful responses to GET and HEAD requests on a version resource.

A storage server MUST include, in successful responses to GET and HEAD requests on a version resource, a Link header with the relation original whose target is the versioned resource.

A version or version history MUST NOT be readable by any agent who cannot currently read the versioned resource.

The service endpoint identifies the versioning service. This draft defines no operation on it. To restore a version, a client reads the version and writes it over the current resource with a conditional request; the server records the result as a new version.

Trash service

ssd:TrashService is a container into which resources are moved instead of being destroyed, and from which they can be restored or purged. Its endpoint is the trash container.

A ssd:TrashService node MAY have one ssd:retention, an xsd:duration after which the storage may purge a trashed resource.

A storage server MUST refuse with 400 Bad Request, without changing anything, a POST request to the trash container whose body does not have exactly one of the members resource and restore.

When a client sends a POST request to the trash container with an application/json body whose resource member is the IRI of a resource in the same storage that the client may delete, the storage server MUST move that resource into the trash and respond 201 Created with a Location header naming the trashed copy.

A storage server MUST refuse a request to trash a resource outside the storage with 400 Bad Request, without reading or changing that resource.

A storage server MUST refuse to trash a resource in the storage that the client may not delete, responding as it would to a DELETE request for that resource by that client.

A storage server MUST include, in successful responses to GET and HEAD requests on a trashed resource, a Link header with the relation original whose target is the IRI the resource had before it was trashed.

When a client sends a POST request to the trash container with an application/json body whose restore member is the IRI of a trashed resource in that trash, and the client may delete the trashed resource and may create a resource at the restore location, the storage server MUST move it out of the trash and respond with a Location header naming the restored resource.

A storage server MUST refuse a restore that the client is not permitted to make, responding 403 Forbidden when the client may read the trashed resource and 404 Not Found otherwise.

A Solid storage server MUST restore a resource to the IRI it had before it was trashed, or refuse the restore with 409 Conflict when that IRI is in use.

A storage server MUST destroy a trashed data resource or empty trashed container when a client with permission to delete it sends a DELETE request to it.

A trashed container that is not empty answers DELETE as any other container does. A client purges it by deleting its members first, or in one request through a recursive delete service.

A trashed resource MUST NOT be readable by any agent who could not read it before it was trashed.

Capability types

Access control

ssd:AccessControl names the authorization model a client must use to read or change who has access: ssd:WAC for Web Access Control [[WAC]], ssd:ACP for Access Control Policy [[ACP]], or ssd:ODRLGrants for ODRL access grants issued through an lws:AccessGrantService.

An ssd:AccessControl node MUST have at least one ssd:model.

A storage server that lists an ssd:AccessControl capability MUST list every authorization model it enforces on the storage.

The access control resource of a particular resource is still found from that resource's Link headers. The capability tells a client which model to expect before it has read any resource.

Patch support

ssd:PatchSupport says which patch document formats the storage accepts for resources of one media type. A storage lists one capability per resource media type.

An ssd:PatchSupport node MUST have exactly one ssd:source, the media type of the resources it applies to.

An ssd:PatchSupport node MUST have at least one ssd:patchType, a patch document media type the storage accepts in PATCH requests on those resources.

The patch types a storage server lists for a media type MUST be a subset of those its Accept-Patch headers announce for resources of that media type.

The Solid Protocol requires N3 Patch on RDF documents, so a Solid storage normally lists text/n3 for text/turtle. The flat shape mirrors the source and target shape of the content negotiation capability in the Linked Web Storage discovery example.

Resumable uploads

An ssd:ResumableUploads node MUST have a dcterms:conformsTo naming the upload protocol, such as https://tus.io/protocols/resumable-upload for [[TUS]].

Pagination

The Solid Protocol returns a container's whole listing in one representation. A storage that splits listings into pages lists ssd:Pagination, so clients know to follow page links.

An ssd:Pagination node SHOULD have a dcterms:conformsTo naming the paging mechanism.

Content negotiation

An ssd:ContentNegotiation node MUST have exactly one ssd:source and at least one ssd:target, each a media type.

A storage server that lists an ssd:ContentNegotiation capability MUST serve every resource stored as its source media type in each of its target media types when a request prefers it.

Subscription types for Linked Web Storage notification services

The Linked Web Storage notification service lists the subscription types it offers with lws:subscriptionType, and the core specification defines only webhooks. Browser clients cannot receive webhooks, so this specification names two streaming subscription types whose bindings are those of the JLWS draft [[JLWS]].

TypeBinding
ssd:SseSubscriptionThe SSE binding of [[JLWS]]: the subscription response carries a source event-stream URL; events carry ids and resume with Last-Event-ID.
ssd:WebSocketSubscriptionThe WebSocket binding of [[JLWS]]: the subscription response carries a receiveFrom wss: capability URL; each message is one notification.

A notification service that lists ssd:SseSubscription or ssd:WebSocketSubscription MUST implement the corresponding binding of [[JLWS]].

A notification service MUST check, for each notification it delivers through these subscription types, that the subscriber may read the resource the notification is about at the time of delivery.

Client processing

Finding the description

A client finds a Solid storage's services and capabilities from any resource in it as follows.

  1. Read the Link headers of a response for the resource.
  2. If they contain the relation https://www.w3.org/ns/lws#storage, the storage is a Linked Web Storage storage: read its description as [[LWS-CORE]] defines, where the subject of the entries is the storage identifier and the storage root is the endpoint of its StorageRoot service. The rest of this list does not apply.
  3. Otherwise, if they contain the relation http://www.w3.org/ns/solid/terms#storageDescription, retrieve its target, preferring application/ld+json or text/turtle, and parse it as RDF.
  4. Find the storage root: the resource itself if its Link headers type it pim:Storage, otherwise the nearest ancestor container whose headers do. If neither exists, the storage root is unknown.
  5. Read the entries as describes.

A client MUST NOT retrieve a storage description, Solid or Linked Web Storage, whose origin differs from the origin of the resource it started from.

A client MUST NOT follow a redirect to another origin while retrieving a storage description.

A client MUST NOT dereference JSON-LD contexts named by a storage description at run time, other than from a cache of contexts it already trusts.

The storage root is the resource itself or one of its ancestors, so it shares the origin of the resource the client started from, and so does every description the client retrieves. A link to a description elsewhere is never dereferenced, which keeps a hostile resource from making the client send requests to other hosts.

A client MUST ignore the did:service and lws:capability statements of a Solid storage description when the storage root is unknown.

A client MUST ignore did:service and lws:capability statements in a Solid storage description whose subject is not the storage root it found.

Reading entries

A client MUST ignore any entry none of whose types it recognises.

A client MUST ignore properties of an entry that it does not recognise.

A client MUST NOT use a service whose type requires a profile unless the client implements at least one of the profiles the service lists.

A client MAY use such a service through any one of its listed profiles that the client implements.

A client MUST treat a subscription service listed with notify:subscription and a ssd:SolidNotificationService with the same endpoint and channel type as one service.

A client MUST treat the object of solid-sparql:endpoint on the storage root as a ssd:SparqlQueryService conforming to [[ACQ]], and as the same service as a ssd:SparqlQueryService with that endpoint.

In the rules below, a service URL is a service endpoint, any URL a service returns for the client to use (such as the source or receiveFrom URL of a notification subscription), and the target of any redirect from either.

A client MUST NOT send credentials it holds for the storage to a service URL whose origin differs from the storage root's origin.

A client MUST NOT send credentials it holds for the storage in a request that follows a redirect to another origin.

A client that is not a web browser MUST NOT send a request to a service URL whose host resolves to a loopback, private-use or link-local address unless the storage root's host resolves to such an address too.

A subscription service on another origin, which the Solid Notifications Protocol allows, is used only with credentials the client obtains for that origin. A web browser already keeps pages from reaching private networks through its own policy; agents and servers that act as clients have no such guard, so they check each endpoint's resolved address, and again after each redirect, before sending a request.

Descriptions, probes and errors

A client SHOULD use the storage description in preference to probing resources for the same information.

A client MUST NOT conclude from the absence of an entry that a storage lacks the behaviour.

A description is not a complete list of what a storage does. A client that finds no entry for a behaviour treats it as unknown: it may probe, or use a fallback that works either way, such as writing collaborative updates as resources when no sync service is listed.

A client MUST NOT treat a storage description as evidence that an agent is permitted to perform an operation.

A client that receives an error from an advertised service SHOULD continue without that service where an alternative exists.

A client MAY cache a storage description for the storage root, subject to the HTTP caching headers of the response that carried it.

Relationship to Linked Web Storage

A Linked Web Storage description is a JSON document whose meaning under its JSON-LD context is an RDF graph. This specification describes the same graph, so the mapping is the identity on IRIs.

idThe storage root IRI (the subject).
type: "Storage"a lws:Storage, alongside a pim:Storage.
service[]did:service
service[].typerdf:type on the service node.
service[].serviceEndpointdid:serviceEndpoint
service[].conformsTodcterms:conformsTo
service[].subscriptionTypelws:subscriptionType

The Linked Web Storage discovery section shows a patch capability as a JSON object keyed by media type. That shape has no RDF meaning under a JSON-LD context, so this specification uses one ssd:PatchSupport per source media type instead.

A Linked Web Storage storage server MAY list the service and capability types this specification defines in its own storage description.

Relationship to other Solid mechanisms

Solid Notifications
notify:subscription stays valid. ssd:SolidNotificationService is the same subscription service listed as a service, so clients that read services find notifications without a second code path.
Type Indexes and Solid Application Interoperability
Type indexes [[SOLID-TYPE-INDEXES]] and interoperability registries [[SAI]] are linked from an agent's profile, not from a storage, and one agent's data can span several storages. A storage description therefore does not point to them. A storage that maintains a server-side index of its own resources lists lws:TypeIndexService and lws:TypeSearchService.
Access-controlled query
The solid-sparql:endpoint link and statement [[ACQ]] stay valid and are read as a ssd:SparqlQueryService.
Server and capability discovery issues
The Solid Protocol issues on a server description (355, with 699 as its duplicate) and on query interface discovery (455, 804) asked where a storage should say what it supports. This specification answers: in the storage description resource, in the Linked Web Storage shape.

Security considerations

A storage description is public metadata about a storage. An attacker who can change it, or who can serve a description for a storage they do not control, can point clients at an endpoint they run. The origin rules in and stop a description on another origin, or an endpoint on another origin, from receiving a client's credentials.

A service can make a client send a request it would not otherwise send, such as a recursive delete. Clients confirm destructive operations with the user as they would without the service, and the server authorizes each request as usual.

A storage description MUST NOT disclose the IRIs of resources that are not themselves public, other than service endpoints and the storage root.

Privacy considerations

A storage description reveals which services a storage offers, and so something about the server software and its configuration. It reveals nothing about the agents who use the storage, because its service and capability statements do not vary with the requester. A storage that hosts one person's data still reveals, through a version history or trash service, that such data may exist; it never reveals the data itself.

Implementation status

The suite's client library @jeswr/storage-capabilities reads both description forms. The sparq server advertises services and capabilities in both its Solid and Linked Web Storage modes. Both predate this draft and differ from it as follows; the differences are tracked for change.

  • sparq lists the notification channel of a ssd:SolidNotificationService with a property ssd:channelType. This draft reuses notify:channelType and defines no ssd:channelType.
  • sparq's Solid mode nests the patch formats under a ssd:format node, and its Linked Web Storage mode uses a mediaType member that no context maps. This draft uses one flat ssd:PatchSupport per source media type.
  • sparq lists a service of type lws:StorageDescription, a term of the JLWS draft that Linked Web Storage does not define. Clients ignore it.
